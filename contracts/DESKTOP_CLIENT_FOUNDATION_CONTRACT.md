## Authorization

The user approved the Phase 150 recommendation and authorized continued normal non-production work without requiring intervention at every step.

Phase 151 is therefore authorized within the exact bounded implementation scope below. This contract does not authorize Phase 152 capability widening or any Phase 154 production mutation.

## Objective

Materialize the first native PRW desktop client foundation while preserving the existing headless Agent authority and the existing local IPC security model.

The phase must produce:

- a Rust GTK 4/libadwaita desktop application crate;
- a restrained native application shell;
- typed presentation state;
- a narrow read-only local Agent IPC client adapter;
- read-only `GetAgentStatus` and `GetPrivateDnsConfig` presentation boundaries;
- deterministic CI validation with required Linux system libraries explicitly installed in CI only;
- authoritative audit evidence.

## Authorized repository changes

Phase 151 may change only:

- root `Cargo.toml` workspace membership;
- root `Cargo.lock` as generated by Cargo for the locked desktop dependencies;
- `apps/desktop/**`;
- `.github/workflows/phase-001-rust-validation.yml` only to install the locked GTK/libadwaita build prerequisites needed after the desktop crate joins the workspace;

- `logs/audits/phase-151-desktop-client-foundation/**`.

No existing Rust domain/protocol/Agent implementation file may be changed by Phase 151 unless a concrete validation failure proves a minimal corrective is required and that corrective is separately recorded.

## Dependency lock

The desktop crate uses exactly the Phase 150 framework choices:

- `gtk4 = 0.11.3`, renamed locally as `gtk`, feature floor `v4_14`;
- `libadwaita = 0.9.1`, renamed locally as `adw`, feature floor `v1_5`;
- path dependency on `prw-agent` for already-validated local IPC types/codecs.

No second UI, async runtime, IPC framework, serialization framework, shell helper, networking stack, analytics SDK, updater, packaging framework, or generic command-execution dependency is authorized in this phase.

## Application identity

The initial application ID is:

`io.patchmirror.prw.desktop`

This identifier is a deterministic non-production application identity for the desktop shell. It is not a package-store identity lock and does not authorize distribution or signing.

## Desktop shell

The first shell must remain intentionally small.

Required visible structure:

- application window titled `Private Remote Workspace`;
- native libadwaita application/window;
- stable left navigation surface on desktop-size windows;
- initial destinations: Overview, Machines, Sessions, Files, Transfers, Activity, Settings;
- Overview is the initial destination;
- read-only Agent status card/surface;
- read-only private-DNS summary surface;
- explicit offline/unavailable/error presentation;
- no false positive connected/encrypted/authorized state.

Unimplemented Phase 152 destinations may present bounded `Not implemented in Phase 151` content. They must not expose mock actions that imply a capability exists.

## Presentation-state model

The desktop crate owns typed presentation state only.

At minimum:

- `AgentAvailability`: `Unknown`, `Offline`, `Connecting`, `Online`, `Error`;
- optional Agent runtime snapshot;
- optional private-DNS snapshot;
- selected navigation destination;
- bounded human-readable detail string derived from typed errors.

Presentation state never grants Agent capability.

## Local IPC client adapter

The Phase 151 adapter is Linux-only and read-only.

It must:

- obtain `XDG_RUNTIME_DIR` from the process environment only as the raw candidate root;
- reject missing, empty, relative, or non-absolute runtime-root values before socket connection;
- derive the socket path only through the existing `prw_agent::LocalIpcContract::socket_path` helper;
- connect only to the fixed filesystem Unix-domain socket;
- apply bounded read/write timeouts;
- generate non-zero request IDs locally;
- use existing PRW request-frame stream encoding;
- use existing PRW response-frame decoders for successful status and private-DNS responses;
- require response request-ID correlation;
- map transport/protocol/Agent-status errors into bounded desktop error categories;
- perform no arbitrary command, shell, filesystem, TCP, D-Bus, abstract-socket, `/tmp`, or fallback-path operation.

The Agent's existing same-UID `SO_PEERCRED` authorization remains the authoritative local peer authentication boundary.

## Runtime behavior boundary

Phase 151 may connect to the already-running local Agent only when the user runs the desktop application.

It must not:

- install, enable, start, stop, restart, or replace the Agent;
- create or delete the Agent socket;
- mutate the PRW runtime directory;
- change systemd state;
- modify network/DNS/firewall/routes;
- provision credentials;
- activate remote transport;
- perform background or boot-time activation.

A failed Agent connection is represented as `Offline` or `Error`; it is not repaired through hidden host mutation.

## Threading/UI boundary

GTK/libadwaita UI work remains on the GTK main thread.

A blocking Unix-socket transaction must not freeze the UI main thread. The initial implementation may use a bounded standard-library worker thread for the two read-only startup queries and marshal the result back to the main context.

No general async runtime is introduced in Phase 151.

## Root CI system dependency correction

Because the root workflow validates all workspace members with all features, after the desktop crate joins the workspace the GitHub-hosted Linux runner must install the native development prerequisites before Cargo validation:

- `pkg-config`;
- `libgtk-4-dev`;
- `libadwaita-1-dev`.

This CI-only package installation is tooling preparation on the disposable GitHub runner. It is not installation on the user's Ubuntu host and is not a production mutation.

The existing Rust commands remain authoritative:

- `cargo metadata --locked --no-deps --format-version 1`;
- `cargo fmt --all -- --check`;
- `cargo clippy --locked --workspace --all-targets --all-features -- -D warnings`;
- `cargo test --locked --workspace --all-targets`;
- `cargo build --locked --workspace --all-targets`.

## Lockfile handling

The root `Cargo.lock` must be generated by Cargo from the candidate source/dependency graph and committed exactly.

Phase 151 must not hand-edit registry package checksums or invent lockfile entries.

A temporary validation branch/workflow may generate the lockfile and validate it before `main` is advanced. The final authoritative `main` must contain the exact validated lockfile.

## Tests

The desktop crate must include focused tests for at least:

- navigation default and deterministic selection;
- presentation mapping for Agent runtime states;
- missing `XDG_RUNTIME_DIR` rejection;
- relative runtime-root rejection;
- fixed socket-path derivation through `LocalIpcContract`;
- bounded error mapping;
- response request-ID mismatch rejection using memory/disposable fixtures without production Agent mutation.

Tests must not bind, unlink, chmod, start, stop, or replace the real Agent socket.
