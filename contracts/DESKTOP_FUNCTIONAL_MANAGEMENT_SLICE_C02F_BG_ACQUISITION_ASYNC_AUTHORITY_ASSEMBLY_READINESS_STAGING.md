## Attempt-ID generation gap

Two distinct fresh non-zero 32-byte attempt domains are required and deliberately remain separate:

1. C02f-AJ `SequenceAllocationAttemptId` for the fence-sequence reservation/allocation operation;
2. C02f-Z `AuthorityAttemptId` for the live-owner mutation operation.

The current typed constructors validate already-generated bytes but do not generate randomness.

C02f-AR explicitly forbids reusing the sequence-allocation attempt ID as the live-owner authority-attempt ID.

`prw-control-plane` currently has no direct RNG dependency selected for this purpose. C02f-BG therefore does not infer an RNG API, OS source, crypto provider, UUID, request-supplied bytes or deterministic derivation.

A later checkpoint must explicitly select generation ownership and prove that both values are fresh, non-zero, non-request-controlled and domain-separated.

## Existing-state / first-owner gap

The current C02f-AB acquisition planner is replacement-oriented: `plan_acquisition(...)` requires one existing validated `LiveOwnerObservation`.

`ReachabilityLiveOwnerEtcdStore::linearizable_observation(peer)` returns `Option<LiveOwnerObservation>`, but no selected acquisition path may convert `None` into an invented predecessor.

Therefore a full implementation of the semantic `acquire(peer)` contract is not yet source-ready for an exact peer whose live-owner key is absent.

C02f-BG finds no currently selected/materialized live-owner absent-key bootstrap transaction that can establish the first retained `PRWL` record while preserving:

- strictly monotonic fencing across recovery;
- exact peer binding;
- sequence-allocation evidence continuity;
- attempt-ID provenance;
- indeterminate mutation reconciliation;
- stale-owner safety.

Missing live-owner state must continue to fail closed until a dedicated first-owner/bootstrap contract is selected and validated.

C02f-BG does not reinterpret `MissingEstablishedState` as contention or successful acquisition.

## Recovery / sequence initialization boundary

Normal acquisition must not issue a recovery epoch.

The existing fence-sequence allocation path assumes a canonical initialized PRWF head. The AP adapter reports missing initialized head rather than manufacturing initialization authority.

Recovery-epoch issuance, Spanner authority, and fence-sequence epoch initialization are separately materialized predecessor mechanisms, but their runtime activation/ownership remains outside normal `acquire(peer)` composition.

A production normal acquisition path may proceed only after the surrounding authority lifecycle has already established that the local PRWF head belongs to the current valid recovery epoch.

No ordinary acquisition may silently initialize or advance recovery epoch state as a fallback.

## Readiness conclusion

C02f-BG classifies the acquisition path as **not yet ready for one-shot full `acquire(peer)` source assembly**.

The blockers are narrower than previously assumed:

1. the downstream `AS -> AE -> AV` composition is already selected by C02f-AW and does not need redesign;
2. normal-path fence-sequence allocation and handoff construction primitives already exist internally;
3. trusted generation ownership for both attempt-ID domains is still unselected;
4. first-owner / absent-live-owner-record bootstrap semantics are still unselected;
5. a narrow control-plane handoff-preparation facade/ownership boundary is still unselected; broad publication of private provider modules is rejected;
6. runtime sequencing that proves the PRWF head is initialized for the current valid recovery epoch remains outside normal acquisition and must not be inferred locally.

## Recommended next checkpoints

The safe sequence after C02f-BG is:

1. select and validate **attempt-ID generation ownership/domain separation**;
2. select and validate **first-owner / absent-live-owner bootstrap semantics**;
3. select a narrow **control-plane acquisition-handoff preparation facade** that composes already-materialized sequence/live-owner primitives without exposing provider internals;
4. only then materialize the full acquisition preparation source;
5. separately materialize the already-selected C02f-AW `AS handoff -> AE -> AV` provider-execution source;
6. only after those pass consider a complete `ReachabilityLiveOwnerAsyncAuthority` production owner/runtime assembly.

The exact ordering of steps 1 and 2 may be reviewed, but neither may be skipped before full `acquire(peer)` assembly.
