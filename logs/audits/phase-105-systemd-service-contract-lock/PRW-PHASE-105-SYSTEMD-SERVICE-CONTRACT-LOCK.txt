USER AUTHORIZATION

The user explicitly approved Phases 105-108 systemd packaging according to Phase 104, using the user-service architecture, while keeping real host activation and linger as a separate later gate.

This authorization covers source-changing non-activating systemd packaging work through Phase 108 only.

It does NOT authorize:

- installing files on the user's host;
- running systemctl --user daemon-reload;
- enabling prw-agent.service;
- starting, stopping, restarting, or reloading the real Agent service;
- creating default.target.wants symlinks on the user's host;
- loginctl enable-linger or disable-linger;
- changing pre-existing linger state;
- deployment;
- public or remote listener activation;
- privileged helper introduction;
- socket activation.

MINIMUM PACKAGING BASELINE

The first systemd package contract targets:

- Ubuntu 24.04 LTS or later explicitly validated Ubuntu release;
- systemd 255.4 or later within that supported baseline;
- a normal per-user systemd manager with a real XDG_RUNTIME_DIR;
- the already-validated same-UID PRW Agent model.

Ubuntu 24.04 is selected because it matches the current permanent CI operating-system family used to validate the standalone Agent and provides the required systemd directive surface without introducing a second operating-system baseline during packaging.

SERVICE IDENTITY LOCK

Service unit name:

prw-agent.service

Service scope:

systemd user service

Process identity:

- existing invoking/user-manager UID;
- no User= directive;
- no DynamicUser=;
- no root-owned runtime process;
- no new service account;
- no privileged helper.

The service manager is not permitted to synthesize XDG_RUNTIME_DIR. The binary consumes the real user-manager runtime environment and retains its existing fail-closed XDG ownership/mode validation.

SOCKET OWNERSHIP LOCK

No .socket unit is permitted in Phases 105-108.

The Agent continues to own:

- instance locking;
- stale-socket inspection/removal;
- bind;
- listen;
- readiness;
- accepted connections;
- socket cleanup.

Systemd socket activation would alter the validated listener ownership model and therefore requires a future architecture gate if ever introduced.

EXECUTABLE / UNIT INSTALL MODEL LOCK

Packaged executable destination:

/usr/lib/private-remote-workspace/prw-agent

Global user-unit destination:

/usr/lib/systemd/user/prw-agent.service

Repository unit source:

packaging/systemd/prw-agent.service

Rationale:

- the executable is system-owned package content but runs unprivileged as the user-service process;
- the unit is globally discoverable by user managers without depending on one user's home directory;
- ExecStart is absolute and does not depend on PATH;
- unit source and executable remain distinct from user-generated configuration/state;
- package installation/upgrade/removal can be separately transaction-audited before activation.

No per-user executable installation under $HOME is part of the initial contract.

[Install]

No additional directive may be added in Phase 106 without being justified as a corrective required for the locked Ubuntu 24.04/systemd 255.4 baseline and recorded explicitly in the Phase 106 authoritative report.

TYPE / READINESS LOCK

Type=exec is selected.

This provides service-manager visibility of successful executable invocation without pretending that the PRW application socket is already ready.

The current Agent does not implement sd_notify and Phases 105-108 must not add Type=notify or a notification dependency.

Application readiness remains proven through the actual Unix socket/protocol boundary, not inferred from systemd ActiveState alone.

RESTART / RATE-LIMIT LOCK

Restart=on-failure
RestartSec=5s
StartLimitIntervalSec=60s
StartLimitBurst=5

Intent:

- restart after unexpected failure;
- do not use Restart=always;
- do not create a tight deterministic crash loop;
- a deliberate systemctl stop operation must not be converted into an automatic restart transaction;
- the Agent's normal handled SIGTERM/SIGINT success path remains a successful terminal path.

STOP LOCK

TimeoutStopSec=15s

No ExecStop= is permitted in the first service unit.
No custom KillSignal= is required; normal service-manager SIGTERM stop behavior is retained.
No second shutdown protocol is introduced.

The timeout is a service-manager outer bound only; it does not replace the Agent's own cancel/join/socket-cleanup/signal-mask-restoration transaction.

LOGGING LOCK

StandardOutput=journal
StandardError=journal

No logging framework dependency, log file, log rotation subsystem, request dump, payload dump, private-key dump, or per-loop verbose logging is introduced.

The standalone binary's existing bounded stderr startup/terminal record remains the service-facing application outcome record.

INITIAL HARDENING LOCK

UMask=0077
NoNewPrivileges=yes

No aggressive filesystem/home isolation is locked in Phases 105-108 because later PRW product scope includes explicit user-authorized workspace/file access.

The following are intentionally deferred rather than silently enabled:

- ProtectSystem=;
- PrivateTmp=;
- InaccessiblePaths=;
- ReadOnlyPaths=;
- ReadWritePaths=;

Any future hardening expansion must be validated against the actual file/network capability contract first.

LINGER OWNERSHIP / ROLLBACK LOCK

Linger is a separate activation transaction.

Phases 105-108 must not call loginctl enable-linger or disable-linger.

A future activation phase must:

1. capture the exact pre-existing linger state;
2. change linger only if explicitly authorized and necessary;
3. record the resulting state;
4. roll back only a PRW-created change;
5. never disable linger that was already enabled before PRW activation.
