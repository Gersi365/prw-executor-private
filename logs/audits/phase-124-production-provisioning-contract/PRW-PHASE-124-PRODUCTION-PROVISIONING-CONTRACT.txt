FIRST-PROVISIONING SEMANTICS

The initial production provisioning transaction is creation-only.

Before generating a private key it must prove all of the following:
- no encrypted production credential exists at the locked destination;
- the destination is not a symlink;
- no PRW-owned production identity metadata claims an existing identity;
- no persistent PRW credential drop-in already binds another ciphertext;
- the target user identity and XDG roots are resolved and validated;
- the target systemd version/capability path supports the locked credential policy;
- the selected custody tier is recorded before generation.

If any prior production identity artifact exists, first provisioning stops fail-closed. It must not overwrite, rotate, import, repair, or silently replace an identity. Rotation/recovery is a separate future transaction.

PRODUCTION KEY GENERATION

The production device identity is generated locally on the Ubuntu device using the already locked AWS-LC P-256 provider profile.

The generated plaintext payload is canonical PKCS#8 v1 DER and must fit the existing 4096-byte signer/custody bound.

The provisioning implementation must not:
- print the private key;
- place it in an environment variable;
- place it in command-line arguments;
- send it over IPC/network;

Any PRW-owned plaintext memory buffer must be zeroizing.

The preferred encryption implementation transfers the plaintext to `systemd-creds --user encrypt` without a named persistent plaintext file, using a bounded pipe/stdin or equivalently memory-only mechanism validated in Phase 125.

If the target systemd CLI cannot support a memory-only transfer with the required policy, Phase 125 must stop and produce a corrective design. It must not silently fall back to a persistent plaintext file.

CUSTODY POLICY SELECTION

On a supported host where TPM2 is usable and persistent `/var` is available, first provisioning uses the Phase 118 preferred systemd user credential policy:
`TPM2_PLUS_HOST_SECRET`.

No explicit host-key-only override is allowed on such a host during normal first provisioning.

`HOST_KEY_ONLY` may be selected only on a host explicitly classified as lacking usable TPM2 while still meeting the supported fallback contract.
The selected tier becomes immutable metadata for that identity lifetime.

There is no silent downgrade after provisioning.
If a TPM2-bound identity later cannot be decrypted under its original policy, identity-dependent operation fails closed and recovery requires explicit identity replacement/re-enrollment.

ATOMIC ENCRYPTED-BLOB COMMIT

The ciphertext must not become authoritative until all generation/encryption checks pass.

Required shape:
1. validate/create the locked credential directory without following symlinks;
2. create a unique temporary ciphertext target in the same final directory with create-new semantics;
3. produce encrypted credential bytes under the exact logical credential name;
4. require non-empty bounded ciphertext;
5. set/verify user ownership and mode 0600;
6. fsync the ciphertext file;
7. verify destination still does not exist and is not a symlink;
8. atomically rename the temporary ciphertext to the locked destination;
9. fsync the parent credential directory;
10. only then classify encrypted credential persistence as committed.

Initial provisioning must never replace an existing final ciphertext.

The provisioning implementation may invoke `systemd-creds` as the locked system utility but must not invoke a shell to construct the secret-bearing operation.

ACTIVATION-AWARE ROLLBACK

Before external enrollment exists, all artifacts newly created by the first identity rollout are transaction-owned.

If any step after B fails, rollback order is locked:
1. stop attempting forward activation;
2. restore the previous Agent executable bytes/mode/ownership if replacement occurred;
3. remove or restore the transaction-owned credential drop-in;
4. `systemctl --user daemon-reload`;
5. restart/verify the previous Agent service state;
6. only after the previous Agent is proven running and its pre-transaction local IPC readiness is restored may the newly created encrypted identity ciphertext be removed;
7. preserve pre-existing enablement and linger state;
8. verify no temporary plaintext or staging artifacts remain.

Rollback must never delete a pre-existing identity artifact.
First provisioning therefore fails before mutation when any prior identity exists.

Once a device identity has been externally enrolled, the encrypted credential is no longer disposable rollback state. Future upgrade rollback may restore software configuration but must not silently delete/replace the enrolled identity. That lifecycle is reserved for explicit rotation/revocation/re-enrollment semantics.
