RECOMMENDED BINARY BOOTSTRAP CONTRACT

1. Keep `main.rs` thin.

`main.rs` should compose validated domain/runtime inputs and delegate to the Phase 098 callable runtime. Runtime algorithms should remain in library modules and not be reimplemented in the binary.

2. Preserve the existing unprivileged/same-user local runtime model.

The first bootstrap should not add a privileged helper, public listener, TUN, relay, database, or remote transport. Those remain separate architecture domains.

3. Keep private DNS optional.

The binary may construct the existing default/effective private-DNS snapshot, but bootstrap must not make private DNS mandatory for Agent startup or local IPC.

4. Avoid a new general configuration parser in the first bootstrap phase.

The production-local runtime requires bounded values for:
- worker capacity;
- Unix listener backlog;
- per-readiness scheduling attempt budget;
- per-session request budget;
- read I/O budget;
- write I/O budget.

Recommendation: lock one explicit initial bounded default profile in Phase 101 and encode those values in a small bootstrap configuration constructor/constants. Do not introduce TOML/YAML/JSON parsing, mutable live reload, or secret configuration as part of first `main.rs` wiring.

The exact numeric values are intentionally NOT locked by Phase 100. They require explicit Phase 101 decision approval.

5. Keep local command policy explicit.

The initial binary must construct one explicit `BoundedLocalReadPolicy`; it must not infer permissions from process environment or silently broaden the command surface.

Recommendation: Phase 101 explicitly decide whether the already-implemented local read commands are both allowed in the initial service profile. No file/terminal/forwarding/device-management capability expansion belongs in bootstrap.

6. Construct immutable snapshots before entering the runtime.

The initial Agent status snapshot and optional private-DNS snapshot should be validated/constructed before the long-running runtime begins and passed through `LocalLinuxProductionRuntimeInputs`.

Any future dynamic state/config refresh is a later feature and should not be smuggled into bootstrap.

7. Exit mapping must be binary-owned and simple.

Recommended initial mapping:
- clean programmatic shutdown => success exit;
- handled SIGTERM/SIGINT termination with clean terminal transaction => success exit;
- startup/lifecycle failure => failure exit;
- readiness/runtime fail-stop => failure exit;
- listener/socket cleanup failure => failure exit even if original reason was clean shutdown;
- signal-mask restoration failure => failure exit even if original reason was clean shutdown.

Recommendation: use a minimal success/failure process exit contract initially rather than a large unstable numeric taxonomy. Preserve detailed typed reason in the log line/auditable text, not in many exit codes.

Exact binary exit representation is NOT approved by Phase 100.

8. Logging should be bounded and dependency-minimal initially.

Recommendation:
- no new logging framework dependency in the first bootstrap;
- emit bounded deterministic startup/failure/terminal summary to stderr;
- do not print secrets, private-key material, request payloads, filesystem content, or unbounded worker evidence;
- terminal summary may include high-level typed reason, bounded counters, cleanup classification, and mask-restoration classification;
- avoid per-readiness-loop or per-poll logging that could become unbounded/noisy.

This is compatible with later journal capture without making systemd a prerequisite for testing the binary.

9. `main.rs` must not own signal-handler logic.

The binary should call the Phase 098 safe signal-aware runtime. It must not add direct signal handlers, libc FFI, unsafe blocks, or a parallel signal implementation.

10. Preserve `unsafe_code = "forbid"`.

No bootstrap justification currently exists for weakening the workspace unsafe policy.

BINARY VALIDATION REQUIREMENTS BEFORE SYSTEMD

A source-changing bootstrap phase should not be classified complete until controlled binary/subprocess tests prove at minimum:

A. clean startup + SIGTERM
- temporary valid XDG runtime root;
- start the compiled Agent binary;
- wait for validated Agent socket presence/readiness without an arbitrary busy loop;
- send SIGTERM;
- binary exits according to locked success mapping;
- socket pathname is absent after exit.

B. clean startup + SIGINT
- same as SIGTERM with SIGINT.

C. one local request
- start binary in temporary runtime root;
- same-UID local client performs one existing bounded read request;
- validate correlated response;
- terminate cleanly;
- prove cleanup.

D. second-instance exclusion
- start first Agent in temporary runtime root;
- start second Agent with same runtime root;
- second process must fail deterministically with typed/aligned AlreadyRunning startup evidence;
- first Agent remains functional;
- terminate first cleanly;
- prove cleanup.

E. invalid runtime-root failure
- missing/invalid/incorrect-mode XDG runtime root must fail before listener activation and return the locked failure exit mapping.

F. no stale socket after startup/runtime failure where cleanup is possible.

G. binary test must not install or rely on systemd.
