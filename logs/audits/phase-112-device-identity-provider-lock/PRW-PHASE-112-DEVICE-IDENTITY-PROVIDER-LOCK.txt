DECISION

PRW locks AWS-LC through aws-lc-rs version 1.18.0 as the initial production provider for one role only:

DEVICE IDENTITY PUBLIC SIGNATURE VERIFICATION.

This is not a global PRW cryptography provider lock.

The following remain explicitly outside this lock:
- network/transport identity;
- mesh session key agreement;
- TUN/data-plane encryption;
- relay transport security selection;
- control-plane TLS selection;
- password/account authentication;
- Android private-key provider/custody implementation;
- Ubuntu private-key generation/storage implementation;
- device identity signing implementation;
- key attestation;
- identity-key recovery or rotation protocol.

LOCKED IDENTITY PROFILE

The existing Phase 003/004 profile remains authoritative and unchanged:
- signature algorithm: ECDSA over NIST P-256 with SHA-256;
- public-key encoding: DER X.509 SubjectPublicKeyInfo;
- SPKI algorithm identifier: id-ecPublicKey;
- named curve: secp256r1 / NIST P-256;
- signature encoding: DER RFC 3279 ECDSA-Sig-Value.

Provider flexibility must not broaden this profile.

PRODUCTION ABSTRACTION BOUNDARY

Phase 113 implementation must introduce one narrow workspace crate:

crates/prw-device-identity
package name: prw-device-identity

Purpose:
- consume existing PRW typed public identity and signature values;
- strictly validate the locked public-key profile;
- verify signatures over caller-supplied message bytes;
- expose bounded provider-neutral PRW errors.

The crate must not expose AWS-LC types in its public API.

The initial public API should remain minimal and provider-neutral, centered on one verification operation equivalent in semantics to:

verify_device_identity_signature(public_identity, message, signature) -> Result<(), DeviceIdentityVerificationError>

Exact naming may change only for Rust API quality without changing the locked semantics.

PROVIDER-SPECIFIC IMPLEMENTATION BOUNDARY

aws-lc-rs must remain an internal dependency of prw-device-identity.

Required provider version:
=1.18.0

Required mode:
non-FIPS AWS-LC path.

No FIPS compliance claim is introduced.

Phase 113 must attempt the narrowest viable feature set with default features disabled. The preferred first attempt is:

default-features = false
features = ["alloc", "non-fips"]

Reason:
The upstream 1.18.0 manifest declares default features including aws-lc-sys, alloc, ring-io, and ring-sig-verify. PRW's validated production design uses ParsedPublicKey plus canonical DER re-serialization rather than the ring-compatible unparsed verification surface. Features not required by the final implementation should not be enabled merely because they are defaults.

This preferred feature set is not considered proven until Phase 113 compilation and all identity-profile tests pass. If an additional feature is technically required, Phase 113 must record the exact requirement and validate the smallest corrected feature set before promotion. No version change is authorized by this lock without a new evidence-producing audit decision.

CANONICAL SPKI ENFORCEMENT

Phase 111 proved that aws-lc-rs can accept a broader EC public-key input surface than PRW's locked protocol representation.

Therefore Phase 113 must preserve the Phase 111 canonicalization guard:
1. parse with the locked ECDSA P-256/SHA-256 verification algorithm;
2. re-serialize the parsed public key as X.509 SubjectPublicKeyInfo DER;
3. require byte-for-byte equality with the original PRW public identity bytes;
4. reject alternate encodings, trailing bytes, malformed DER, wrong algorithm OID, wrong curve OID, and invalid/off-curve points;
5. only then verify the DER ECDSA signature.

The provider's parser convenience is not the PRW protocol contract.

ERROR BOUNDARY

The production crate must return bounded PRW-owned error classes. The minimum locked classes are:
- UnsupportedProfile;
- InvalidPublicKey;
- NonCanonicalPublicKeyEncoding;
- InvalidSignature.

Provider error types, internal native error codes, and parsing implementation details must not escape through the public PRW API.

PRIVATE-KEY BOUNDARY

The production prw-device-identity crate introduced by this sequence is verification-only.

It must not expose production APIs for:
- key generation;
- private-key import/export;
- signing;
- persistent private-key storage;
- Android Keystore extraction;
- Ubuntu secret storage;
- key backup/recovery.

Disposable signing keys may remain test-only fixtures where required to prove verification behavior.

CRATE DEPENDENCY DIRECTION

The new crate may depend on the existing transport-neutral domain types currently defined by prw-control-plane.

prw-control-plane must not be changed to depend back on prw-device-identity in Phase 113. This prevents a dependency cycle and keeps the current domain-action crate provider-neutral.

No existing Agent dependency on prw-device-identity is authorized by Phase 112.

The resulting initial dependency direction is:

prw-device-identity -> prw-control-plane -> prw-core
prw-agent -/-> prw-device-identity

A later enrollment/authentication orchestration layer may consume both prw-control-plane domain actions and prw-device-identity verification without forcing the domain crate to own the provider.

FOOTPRINT TREATMENT

Phase 111 measured an isolated release footprint delta of approximately 2,670,920 bytes for a small aws-lc-rs P-256 parsing probe relative to an empty Rust probe.

This cost is accepted for the narrow device-identity verification role, but the architecture must not pull AWS-LC transitively into binaries that do not need device-identity verification.

Phase 113 must prove that prw-agent remains outside the provider dependency path and that its release binary remains materially unchanged within normal toolchain/build variance.
