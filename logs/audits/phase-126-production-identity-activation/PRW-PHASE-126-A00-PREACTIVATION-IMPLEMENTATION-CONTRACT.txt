PURPOSE

Phase 124 locked a production activation postcondition requiring proof that the identity-aware Agent loaded the same canonical public identity derived from the newly provisioned production private key.

Phase 125 proved only that an identity-aware candidate can load a disposable systemd credential and become Ready. The current local GetAgentStatus protocol intentionally exposes only runtime state and protocol version; it does not expose public device identity.

Phase 126 must not create the production private key until there is a deterministic, non-secret proof surface that binds:
1. the locally generated production identity;
2. the encrypted credential committed to XDG state;
3. the systemd-delivered runtime credential;
4. the signer actually loaded by the activated Agent.

LOCKED ATTESTATION DESIGN

The local IPC protocol remains version 1.0 and is not expanded solely for activation evidence.

Instead, the identity-aware Agent emits one bounded startup attestation before entering the existing runtime lifecycle:

`prw-agent event=device_identity_loaded public_spki_sha256=<64-lowercase-hex>`

The fingerprint is SHA-256 over the exact canonical X.509 SubjectPublicKeyInfo DER bytes returned by the loaded signer.

The fingerprint is public/non-secret identity metadata. No PKCS#8/private scalar/signature material is logged.

The attestation occurs only after:
- Phase 122 custody validation passes;
- canonical signer construction passes;
- canonical public SPKI exists.

It occurs before:
- instance lock acquisition;
- Agent socket/listener creation;
- Ready state.

If identity loading fails, the existing Phase 125 single bounded startup failure remains unchanged and no fingerprint is emitted.

The signer/provider boundary should own SHA-256 fingerprint computation over its canonical public identity so `prw-agent` does not add a direct production AWS-LC dependency.

PROVISIONING IMPLEMENTATION REQUIREMENT

Phase 125 demonstrated memory-only `keygen | systemd-creds` compatibility using temporary workflow helpers, but it did not commit a reusable production provisioning implementation.

Before production identity creation, Phase 126-A01 must implement a narrow production provisioning boundary that:
- generates a fresh ECDSA P-256 private identity locally;
- canonicalizes/validates PKCS#8 v1 DER under the already locked signer profile;
- computes the canonical public SPKI SHA-256 fingerprint;
- resolves the locked XDG state ciphertext path;
- validates creation-only semantics and all parent/leaf ownership/mode/symlink constraints;
- invokes `/usr/bin/systemd-creds --user encrypt --name=prw.device-identity.private-key.v1 - <same-directory-temp-target>` directly with `std::process::Command`, never through a shell;
- writes private PKCS#8 bytes only to the child process stdin pipe;
- zeroizes every PRW-owned plaintext private-key buffer after transfer;
- captures only bounded non-secret subprocess diagnostics;
- verifies non-empty ciphertext and secure mode/ownership;
- fsyncs file and parent directory;
- atomically commits to the locked final ciphertext path without replacing an existing identity;
- returns/prints only the public fingerprint and non-secret destination/classification metadata.

The production provisioner must not expose an existing-key export API and must not accept arbitrary caller-supplied private-key bytes for first provisioning.

PROVISIONER FORM

A dedicated internal workspace crate/binary is preferred:
`prw-device-identity-provisioning`

Its public library surface, if any, must remain creation-only and narrow. It must not become a generic key-management toolkit.

Its command-line surface must not accept private key material, passwords, secret environment variables, or alternate arbitrary credential names/paths.

Production path is derived from validated XDG/HOME policy; the logical credential name is compile-time fixed.
