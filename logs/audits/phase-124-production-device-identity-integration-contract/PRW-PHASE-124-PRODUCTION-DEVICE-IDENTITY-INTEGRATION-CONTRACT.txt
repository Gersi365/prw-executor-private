PROVISIONING OWNERSHIP

Production Ubuntu device-identity provisioning is an explicit, bounded, one-shot local transaction.

It is NOT an implicit side effect of:
- normal Agent startup;
- Agent restart;
- missing-credential recovery;
- enrollment request receipt;
- remote network traffic;
- systemd service activation.

If no production identity exists, normal Agent startup must not silently create one.

The provisioning implementation must have a narrow local entry point dedicated to device identity. It must not expose arbitrary secret generation, arbitrary file encryption, arbitrary command execution, or generic signing.

CURRENT POWERCODE CUSTODY POLICY

PowerCode has already proven usable TPM2 capability and successful systemd default user-scoped encrypted-credential delivery.

Therefore the first production provisioning transaction on PowerCode is locked to:
TPM2_PLUS_HOST_SECRET

The implementation must not request HOST_KEY_ONLY on this host as an automatic retry or compatibility fallback.

If the TPM2-capable default encryption path fails, provisioning fails closed before production activation.

HOST_KEY_ONLY remains architecture-supported only as a future explicit lower-tier provisioning decision for a host where TPM2 is not usable and product policy explicitly permits fallback.

KEY GENERATION AND PLAINTEXT LIFETIME

The production private key profile remains:
- ECDSA P-256;
- canonical PKCS#8 v1 DER custody payload;
- canonical X.509 SPKI public identity;
- SHA-256 / ASN.1 DER ECDSA signature profile already locked by Phases 113-121.

The provisioning transaction must:
1. generate a fresh P-256 identity using the already locked cryptographic provider;
2. derive the canonical public identity before activation;
3. hold any PRW-owned plaintext PKCS#8 bytes in a bounded zeroizing owner;
4. never log, serialize to audit, return over IPC, or persist the plaintext private bytes as normal PRW state;
5. hand the bounded payload only to the fixed systemd encrypted-credential creation boundary;
6. drop/zeroize PRW-owned plaintext buffers immediately after encryption/verification handoff.

Phase 125 must prove a no-persistent-plaintext provisioning path. If the selected systemd interface cannot be used without creating a named persistent plaintext key file, Phase 125 must stop and classify the interface gap rather than silently weakening this contract.

ENCRYPTED CREDENTIAL TARGET

The production ciphertext target remains:
${XDG_STATE_HOME:-$HOME/.local/state}/private-remote-workspace/credentials/device-identity-private-key-v1.cred

Required transaction properties:
- resolve the XDG state root for the target user before mutation;
- credential directory owned by the PRW user and mode 0700;
- encrypted blob owned by the PRW user and mode 0600;
- no symlink following for directory/blob creation or replacement;
- candidate written to a fresh temporary sibling in the same protected directory;
- candidate fully flushed before activation;
- final promotion by atomic same-directory replacement only after verification;
- an unknown or foreign pre-existing final target fails closed;
- first provisioning must not overwrite an existing production blob;
- replacement of an existing valid identity belongs to a separate rotation transaction.

AGENT STARTUP / READINESS SEMANTICS

Once the production credential drop-in is activated, the Agent must load the Ubuntu enrollment signer through the exact Phase 122 custody function during bounded startup before publishing normal Ready state.

Locked ordering:
1. validate existing process/runtime prerequisites;
2. acquire the existing single-instance ownership boundary;
3. load the fixed systemd-delivered device-identity signer;
4. only after successful custody load may the Agent progress to normal listener/readiness publication.

If systemd cannot decrypt/deliver the credential, service activation fails closed before Agent startup.

If the Agent receives the credential but the custody/signer boundary rejects it, the Agent exits with a bounded non-secret identity-custody failure before Ready.

The Agent must not report normal Ready while the configured production identity is unavailable or invalid.

The existing signal/shutdown precedence and local IPC security boundaries remain unchanged.

FIRST-PROVISIONING TRANSACTION ORDER

A future real production provisioning transaction must use this high-level order:
1. capture authoritative repository head and real-host pre-state;
2. verify current Agent executable/unit hashes, enabled/active state, linger state, XDG roots, systemd user manager, and TPM2-capable custody policy;
3. prove final production ciphertext target and managed drop-in do not already contain an authoritative identity/configuration;
4. generate a fresh candidate identity in bounded memory;
5. derive candidate canonical public identity;
6. create the candidate systemd encrypted credential under the fixed name and selected policy;
7. verify candidate delivery/load/public-identity equality through a disposable transient user-service path;
8. atomically promote the ciphertext candidate to the final protected XDG state path;
9. atomically install the managed per-user drop-in referencing that exact final absolute path;
10. systemctl --user daemon-reload;
11. restart prw-agent.service in a bounded transaction;
12. verify active/running state and the existing local IPC Ready contract;
13. verify no plaintext key artifact remains;
14. only after all preceding checks pass may a later enrollment phase use the signer.

ROLLBACK BEFORE ENROLLMENT

Until the new public identity has been accepted by an enrollment authority, the provisioning transaction is locally reversible.

If any activation check fails after candidate promotion but before enrollment:
- stop the failed new activation if required;
- restore the exact pre-transaction drop-in state;
- remove the newly created un-enrolled ciphertext only if it was created by this transaction and no prior identity existed;
- daemon-reload;
- restore the prior Agent service state;
- verify prior executable/unit hashes, enablement, linger, and local IPC state;
- preserve bounded audit evidence without preserving private plaintext.

A failed first-provisioning transaction must not leave a partially authoritative device identity.

ROTATION / RE-ENROLLMENT SEPARATION

If a production encrypted identity already exists, first-provisioning logic must fail closed.

Identity replacement is not an overwrite case. It is a separate rotation/re-enrollment lifecycle requiring:
- old/new public-identity coordination;
- explicit authorization semantics;
- atomic authority transition;
- rollback rules that account for server-side enrollment state.

Phase 124 does not authorize or implement rotation.

ENROLLMENT SEPARATION
