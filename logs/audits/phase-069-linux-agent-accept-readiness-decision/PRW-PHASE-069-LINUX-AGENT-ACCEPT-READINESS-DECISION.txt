PURPOSE

Lock the accept blocking/readiness policy and accepted-peer security ordering before introducing the first production accept operation for the filesystem-backed Linux PRW Agent listener.

EVIDENCE REVIEWED

The review confirmed the current validated/runtime contracts already establish:

- Phase 052 caller-bounded application Request processing over an already-authenticated generic stream;
- Phase 053 requirement that accepted streams must pass kernel SO_PEERCRED same-UID authentication before application processing;
- Phase 058 same-effective-UID authorization with no application-byte consumption;
- Phase 059 typed authenticated connected-stream ownership;
- Phase 060 authenticated application-session composition;
- Phase 064 mandatory accepted-connection ordering;
- Phase 065 single-instance authority;
- Phase 066 locked stale socket-path transaction;
- Phase 067 descriptor-anchored bound socket with post-bind identity/mode validation;
- Phase 068 one-way bound-to-listening transition with explicit caller backlog and no accept/readiness policy.

DECISION 1 — EXPLICIT ACCEPT-READY TYPE STATE

A production accept operation must not be callable on plain Phase 068 ListeningAgentSocket.

Phase 070 is authorized to introduce the one-way transition:

ListeningAgentSocket -> AcceptReadyAgentSocket

The transition must read descriptor status flags, set O_NONBLOCK while preserving current flags, read them again, and return AcceptReadyAgentSocket only after O_NONBLOCK is verified.

If readiness preparation fails, the original ListeningAgentSocket must be returned with a bounded transition error so the caller retains existing cleanup authority.

CORRECTIVE TO INITIAL DRAFT

The first Phase 069 draft proposed setting nonblocking at Phase 067 socket creation time. Pre-implementation review found a stronger type-state design: leave validated Phase 067/068 semantics unchanged and make nonblocking readiness an explicit post-listen transition.

This corrective changes only the mechanism, not the required security property. Accept remains impossible until the listener is proven nonblocking.

Benefits:

- no retroactive semantic rewrite of the already validated Phase 067 construction baseline;
- explicit type-level proof that readiness preparation happened;
- failure can retain the valid listening object for safe cleanup;
- accept policy remains isolated from bind/listen policy.

DECISION 2 — ONE-SHOT ACCEPT ONLY

The accept-ready adapter performs at most one kernel accept attempt per invocation.

Outcomes are separated into:

- authenticated connection accepted;
- no connection currently ready (EAGAIN/EWOULDBLOCK) as a normal readiness outcome;
- bounded accept failure;
- bounded peer-authorization failure.

The adapter performs no internal retry, spin, sleep, poll, timeout, thread/task creation, or accept loop.

DECISION 3 — ACCEPTED STREAM REMAINS BLOCKING

The listener is verified nonblocking, but the accepted connected stream remains blocking.

The accepted descriptor must be close-on-exec and must not request a nonblocking accepted-socket flag.

This preserves the already validated Phase 059/060 std::io::Read/Write behavior. Phase 070 tests must verify the actual accepted-stream status flags on the Linux runner.

DECISION 4 — AUTHENTICATION IS IMMEDIATE AND TYPE-GATED

The accepted raw connected stream remains inside the Linux crate-internal adapter.

Mandatory ordering:

accept -> Phase 059 AuthenticatedLocalLinuxConnection::try_new -> Linux SO_PEERCRED -> exact same-effective-UID authorization -> only then expose authenticated connection/session construction.

On authentication failure the rejected stream is closed/dropped before returning the bounded authorization error. No PRW application-protocol byte may be read first.

DECISION 5 — LISTENER LIFECYCLE IS UNAFFECTED BY ONE ACCEPT

Accepting, rejecting, or observing no-ready must not alter:

- agent.sock filesystem identity or mode;
- the validated PRW runtime-directory descriptor;
- the Phase 065 instance lock;
- stale-path/bind/cleanup ownership;
- listener backlog state beyond normal kernel queue behavior.

AcceptReadyAgentSocket owns the Phase 068 ListeningAgentSocket and delegates explicit cleanup through the already validated Phase 068/067 lifecycle.

DEFERRED ORCHESTRATION

Phase 069 deliberately does not choose:

- poll/ppoll/epoll;
- an async runtime;
- a listener thread;
- accept batching;
- connection concurrency limits;
- wall-clock timeout policy;
- cancellation;
- per-connection worker/task scheduling;
- Agent bootstrap/service wiring.

These are higher-level runtime orchestration decisions and are not needed to implement a safe nonblocking one-shot accept primitive.

NEXT SAFE IMPLEMENTATION

Phase 070 may implement only:

1. the explicit ListeningAgentSocket -> AcceptReadyAgentSocket O_NONBLOCK transition with post-write verification;
2. a crate-internal one-shot accept operation exposed only by the accept-ready type;
3. close-on-exec accepted descriptor creation without accepted-stream NONBLOCK;
4. conversion to the existing connected Unix stream type;
5. immediate Phase 059 same-UID authenticated wrapper construction;
6. typed no-ready / accept-failure / authorization-failure outcomes;
7. focused temporary Linux tests proving nonblocking listener + blocking authenticated accepted stream semantics.

Phase 070 must not implement an accept loop, application session loop wiring, bootstrap activation, systemd activation, or runtime concurrency.

MUTATION STATEMENT
