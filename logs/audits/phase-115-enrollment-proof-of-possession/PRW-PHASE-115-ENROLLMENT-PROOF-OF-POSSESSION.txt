3. PROVIDER-NEUTRAL ENROLLMENT PoP DOMAIN

The new control-plane enrollment PoP module defines the following locked constants and bounds:

- domain separator: exact bytes "PRW\0EnrollmentProofOfPossession\0"
- proof-message version: 1
- challenge nonce length: exactly 32 bytes / 256 bits
- maximum UTF-8 identifier length in a proof message: 1024 bytes per identifier
- maximum public-identity length for the initial profile: 256 bytes
- maximum canonical proof-message length: 4442 bytes
- maximum challenge lifetime: 300 seconds

The module defines typed values for:

- EnrollmentProofNonce
- EnrollmentProofChallenge
- EnrollmentProofOfPossession
- EnrollmentProofChallengeState

The proof value submitted by a device contains only:

- EnrollmentId
- challenge nonce
- device-identity signature

Security-critical workspace, user, device, algorithm, encoding, and public-key binding data are not accepted as duplicate proof fields. They are reconstructed from the server-owned immutable EnrollmentRequest snapshot.

4. SERVER-OWNED CHALLENGE SEMANTICS

EnrollmentProofChallengeState owns:

- the immutable EnrollmentRequest snapshot;
- the current active challenge;
- the consumed state.

Challenge lifetime must be in the inclusive range 1..=300 seconds.

The verifier owns issued_at and expires_at timestamps. Client/device time is not trusted for challenge lifetime, and timestamps are deliberately not included in the signed canonical message.

Submission context validation fails closed in this order:

1. already consumed;
2. verifier time before issue time;
3. verifier time at or after expiry;
4. enrollment identifier mismatch;
5. nonce mismatch.

A successfully verified challenge is single-use. consume_verified() revalidates the current proof context before committing consumed=true.

Replacing the current challenge:

- preserves the same immutable enrollment request snapshot;
- replaces the nonce and server-owned lifetime;
- invalidates the previous nonce;
- clears consumed state for the replacement challenge.

A future persistent implementation must preserve equivalent compare-and-consume semantics transactionally.

5. CANONICAL SIGNED MESSAGE

The canonical proof message is reconstructed only from:

- the immutable server-side EnrollmentRequest snapshot;
- the exact current server challenge nonce.

The encoding binds, in order:

- exact domain separator;
- u16 proof-message version;
- length-prefixed EnrollmentId;
- length-prefixed WorkspaceId;
- length-prefixed UserId;
- length-prefixed DeviceId;
- explicit u16 device-identity algorithm code;
- explicit u16 public-key encoding code;
- length-prefixed public identity bytes;
- exact 32-byte nonce.

Length prefixes are bounded and encoded deterministically. Size arithmetic is checked. The exact locked maximum encoded size is 4442 bytes.

Changing any bound field changes the signed message.

6. PRODUCTION VERIFIER COMPOSITION

The Phase 113 production device-identity crate now composes enrollment PoP verification in the following strict sequence:

1. validate server-owned submission context;
2. canonical-encode the bound snapshot and current nonce;
3. verify the signature with the locked P-256 / SHA-256 / canonical DER SPKI device-identity verifier;
4. consume the challenge only after successful cryptographic verification.

Failure classes preserve the boundary between:

- submission/context rejection;
- canonical-message construction rejection;
- device-identity cryptographic verification rejection.

Invalid cryptographic proofs do not consume challenge state.

No production EcdsaKeyPair, SystemRandom signing path, .sign() operation, private-key generation/import/export, or private-key persistence surface was added to prw-device-identity.
