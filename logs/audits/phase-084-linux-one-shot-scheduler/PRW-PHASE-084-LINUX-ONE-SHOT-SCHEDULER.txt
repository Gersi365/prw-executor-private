PURPOSE

Compose the validated local Linux runtime primitives into exactly one capacity-gated scheduling attempt without introducing an accept loop, poller, or Agent bootstrap activation.

IMPLEMENTED

- source: crates/prw-agent/src/linux_one_shot_scheduler.rs

STRICT ORDERING

One scheduling call performs:

1. acquire one Phase 075 worker permit;
2. if capacity is full, return AtCapacity without touching the listener;
3. perform exactly one Phase 070 authenticated accept attempt;
4. if no connection is queued, release the temporary permit and return NoConnectionReady;
5. create the Phase 082 cancellation clone while borrowing the authenticated accepted connection;
6. consume the accepted outcome through the Phase 071 authenticated-session bridge;
7. spawn exactly one Phase 078 scoped worker using the Phase 076 worker configuration and only the Phase 083 BoundedLocalReadPolicy;
8. register the scoped handle together with its matching cancellation authority in the Phase 080/082 registry;
9. return WorkerRegistered.

POLICY BOUNDARY

The scheduling API accepts only BoundedLocalReadPolicy. It does not accept a generic/arbitrary PolicyEvaluator, preserving the Phase 081 restriction against potentially blocking external policy evaluation in the initial runtime path.

FAIL-CLOSED BEHAVIOR

- capacity full: zero accept attempt;
- no-ready: acquired permit released and no registry entry;
- accept failure: owned permit/connection state is dropped;
- cancellation-clone failure: connection is not spawned;
- scoped-spawn failure: captured session/permit are disposed through the fallible spawn path and local cancellation authority is dropped;
- registry mutation occurs only after successful worker spawn.

VALIDATED BEHAVIOR

Linux runner tests prove:

- a client/Request already queued in the kernel listener queue is not consumed while worker capacity is full;
- after the held permit is released, the same queued connection is accepted, scheduled, processed, and produces the correlated response;
- NoConnectionReady releases the temporary capacity permit and creates no registry entry;
- successful scheduling creates exactly one worker registry entry and one active worker slot;
- the scheduled idle worker can be cancelled and joined through the Phase 082 registry path;
- capacity returns to zero after worker completion/cancellation;
- existing listener lifecycle cleanup remains authoritative.
